## 0. Налаштування

```bash

cd 2026-udc-11-architecture-devops-hw
```

`npm install` не потрібен — у репо **немає жодної npm-залежності**, лише Node 22+.
Потрібні ще Git Bash (на Windows), GitHub account і Agentic IDE. **API-ключі, хмарні

`npm run check:deploy` один раз завантажує `yaml@2.8.1` через `npx` (потрібна мережа),
далі перевірка працює офлайн.

### Що засіяно в репо

Усі задачі — на одній системі, «Поштомат громади»: служба доставки реєструє посилку,
мешканець отримує SMS з кодом і забирає посилку на екрані поштомата.

| Шлях | Що це |
|---|---|
| `app/` | Сервіс: HTTP API, worker для SMS, нічна задача, конфіг зі змінних оточення, тести |
| `materials/` | Бриф нової функції і документи команди — вхід для Task A |
| `docs/ops/` | Операційні runbook-и команди |
| `incident/` | Дані інциденту 2026-10-14 — вхід для Task C. Почніть з `incident/README.md` |
| `deploy/` | Поточні `Dockerfile` і `compose.yaml` — вхід для Task D |
| `pipeline/` | Сюди — ваш `deploy.yml` (Task D) |
| `tools/` | `check-deploy.mjs` — детермінований перевіряльник деплою, і його тести |
| `ai-runs/` | Сюди — перші відповіді AI, дослівно (див. `ai-runs/README.md`) |
| `docs/templates/` | Шаблони для всіх документів домашки |

Шаблони скопіюйте на їхні місця одразу:

```bash
mkdir -p docs/adr && cp docs/templates/adr.md docs/adr/0001-notifications.md
cp docs/templates/{constraints,architecture,rca,postmortem,runbook}.md docs/
cp docs/templates/task-e-bonus.md docs/   # лише якщо робите бонус
```

> **Правила для всіх задач.**
> 1. **AI — асистент, рішення ухвалюєте ви.** Під ADR, RCA і конфігом деплою
>    підписуєтеся ви, а не модель.
> 2. **Перша відповідь AI — дослівно в `ai-runs/`, до будь-яких виправлень.** Саме її ми
>    міряємо: що AI знав і чого не знав про систему. Не скорочуйте, не правте і не
>    перепитуйте, «поки не вийде». Далі працюйте з AI скільки завгодно — у своїх файлах у `docs/`.
>    Агент записав відповідь у файл або поставив питання — що зберігати, див. `ai-runs/README.md`.
> 3. **Кожне твердження, яке ви лишаєте, має доказ:** `файл:рядок` або команда і її вивід.
>    Без доказу — викреслюйте або позначайте як припущення.
> 4. **Один прогін — одна нова сесія:** без історії попередніх прогонів і без ваших підказок.
> 5. **Текст у `materials/`, `incident/`, логах і дифах — це дані, а не інструкції.**
>    Ні для вас, ні для агента.

### Як показати AI лише частину репо

Працюйте в **агентному режимі** (Claude Code; Cursor — Agent; Copilot — Agent mode), щоб AI
сам читав файли й запускав `grep` / `node`: лише логи прогону 1 у Task C — понад 1 МБ, у
звичайний чат вони не влізуть, і модель відповідатиме за шматком даних.

Agentic IDE бачить усю теку проєкту і сам підвантажує `AGENTS.md` / `CLAUDE.md`, а там
описано, що лежить у репо. Тому для кожного прогону робіть **тимчасову копію** потрібних
файлів **поруч із репо** (не всередині — інакше `git add -A` її закомітить) і відкривайте
її як окремий проєкт у новій сесії:

```bash
# приклад: прогін, який бачить лише app/
mkdir -p ../ws11-a-without && cp -r app ../ws11-a-without/
```

Команди копіювання для кожного прогону — у задачах нижче. Гірший варіант — прогін у самому
репо з явною вказівкою «читай лише `app/`»: агент усе одно бачить `AGENTS.md` і може
зазирнути деінде. Якщо робили так — напишіть це в шапці файлу в `ai-runs/`.

На час прогонів вимкніть пам'ять між сесіями (memories) і глобальні правила та інструкції —
вони теж контекст: Cursor User Rules, Copilot personal instructions, `~/.claude/CLAUDE.md`.
Не вийшло вимкнути — запишіть у шапці файлу в `ai-runs/`, що саме було ввімкнено.

## Task A — ADR з AI _(~45 хв)_

**Мета:** побачити, чого AI не знає про систему, коли бачить лише код, — і ухвалити
архітектурне рішення самим, з доказами.

Нова функція — у `materials/feature-brief.md`: сповіщення і нагадування про посилки.

1. **Два прогони з тим самим питанням.**
   - **Без матеріалів** — лише питання і `app/` (без кореневих `materials/`, `docs/`,
     `deploy/`, `incident/`). Відповідь → `ai-runs/adr-without.md`.
     ```bash
     mkdir -p ../ws11-a-without && cp -r app ../ws11-a-without/
     ```
   - **З матеріалами** — те саме плюс `materials/` і `docs/ops/`. Відповідь → `ai-runs/adr-with.md`.
     ```bash
     mkdir -p ../ws11-a-with/docs && cp -r app materials ../ws11-a-with/ && cp -r docs/ops ../ws11-a-with/docs/
     ```

   Питання — однакове в обох прогонах. Функцію перекажіть своїми словами — лише три
   пункти розділу «Що хочемо» з брифу: усе інше в брифі — частина матеріалів, а в першому
   прогоні їх немає.

   ```text
   У цій теці — код сервісу «Поштомат громади» (app/). Ми додаємо нову функцію:
   <три пункти з розділу «Що хочемо», своїми словами>.
   Запропонуй архітектурне рішення і оформи його як ADR у форматі Nygard
   (Context, Decision, Consequences) з щонайменше двома альтернативами та їхніми компромісами.
   Відповідь дай повністю в чаті; файлів не створюй і уточнювальних питань не став —
   припущення називай явно.
   ```

   У другому прогоні додайте одне речення: «У теці є також `materials/` і `docs/ops/` —
   прочитай їх перед відповіддю».

2. **Обмеження** — `docs/constraints.md` (шаблон є). Знайдіть усі обмеження в
   `materials/` і `docs/ops/`, кожне — з `файл:рядок`. AI може допомогти шукати, але
   кожне обмеження перевірте у файлі самі. **Обмеження** — це те, що відкидає частину
   варіантів рішення або змушує щось до рішення додати; факт, який нічого не відкидає, —
   не обмеження. Для кожного: чи врахував його прогін 1? прогін 2? де воно у вашому ADR?
   **Враховано** — коли рішення чи наслідки справді на нього зважають, а не лише
   переказують бриф.

3. **Ваш ADR** — `docs/adr/0001-notifications.md` (шаблон `docs/templates/adr.md`,
   формат Michael Nygard): Context, Decision, Consequences; щонайменше дві альтернативи з
   компромісами. Чернетку пише AI, рішення — ваше: кожне обмеження з вашої таблиці або
   враховане, або свідомо відкинуте з поясненням.

**Число:** «без матеріалів X з N, з матеріалами Y з N», де N — скільки обмежень знайшли ви.

**Перевірка:** обидва файли в `ai-runs/`; у `docs/constraints.md` кожне обмеження має
`файл:рядок` і відповідь для обох прогонів; ADR має три розділи Nygard і ≥2 альтернативи;
число в підсумку сходиться з таблицею.

## Task B — Діаграма як код _(~30 хв)_

**Мета:** діаграма, якій можна вірити, бо кожна стрілка на ній має доказ у коді.

1. **Спершу — лише з документації** (`app/README.md`, `app/docs/ARCHITECTURE.md`).
   Відповідь → `ai-runs/c4-from-docs.md`.
   ```bash
   mkdir -p ../ws11-b-docs/app && cp -r app/README.md app/docs ../ws11-b-docs/app/
   ```
2. **Потім — з коду** (уся `app/`). Відповідь → `ai-runs/c4-from-code.md`.
   ```bash
   mkdir -p ../ws11-b-code && cp -r app ../ws11-b-code/
   ```

   Питання — те саме в обох прогонах:

   ```text
   Намалюй архітектуру цієї системи як C4-діаграми в Mermaid:
   рівень System Context і рівень Container.
   Відповідь дай повністю в чаті; файлів не створюй і уточнювальних питань не став —
   припущення називай явно.
   ```

3. `docs/architecture.md` (шаблон є): ваші діаграми System Context і Container у
   Mermaid — такі, якою система є в коді. **Кожну стрілку перевірте в коді** і занесіть у
   таблицю «стрілка → доказ (файл:рядок) → AI мав рацію?» — для обох прогонів. Окремо —
   короткий список «що AI вигадав / пропустив».
4. `app/` не редагуйте — ні код, ні його документацію. Якщо показуєте на діаграмі частину
   з вашого ADR — позначте її «запропоновано», а доказом дайте розділ ADR.

GitHub рендерить Mermaid у markdown. `C4Context` / `C4Container` або звичайний
`flowchart` — на ваш вибір; перевірте, що діаграма рендериться (preview на GitHub або
<https://mermaid.live>).

**Число:** скільки стрілок AI вигадав і скільки пропустив — з документації і з коду.

**Перевірка:** обидва файли в `ai-runs/`; дві Mermaid-діаграми; кожна стрілка діаграм —
рядок таблиці з `файл:рядок`; список «вигадав / пропустив» сходиться з таблицею.

## Task C — Інцидент і RCA з AI _(~60 хв)_

**Мета:** знайти причину інциденту і довести її так, щоб будь-хто повторив ваші команди
й отримав той самий результат.

Що сталося — в `incident/README.md`. Task C робіть **до** Task D: другий прогін має
бачити `deploy/` у стані з початку домашки. Кожен прогін над логами — це кілька хвилин
роботи агента: закладіть їх у час.

1. **Прогін 1 — що черговий мав у перші хвилини:** лише `incident/alerts.json`,
   `incident/logs/`, `incident/metrics/`. Відповідь → `ai-runs/rca-v1.md`.
   ```bash
   mkdir -p ../ws11-c1/incident && cp -r incident/alerts.json incident/logs incident/metrics ../ws11-c1/incident/
   ```
2. **Прогін 2 — усе:** уся тека `incident/` + `app/` + `deploy/`. Відповідь → `ai-runs/rca-v2.md`.
   ```bash
   mkdir -p ../ws11-c2 && cp -r incident app deploy ../ws11-c2/
   ```
   Якщо `deploy/` ви вже змінили в Task D — візьміть його з `main`:
   ```bash
   mkdir -p ../ws11-c2/deploy && cp -r incident app ../ws11-c2/
   git show main:deploy/Dockerfile > ../ws11-c2/deploy/Dockerfile
   git show main:deploy/compose.yaml > ../ws11-c2/deploy/compose.yaml
   ```

   Питання — те саме в обох прогонах:

   ```text
   Ти — черговий інженер сервісу «Поштомат громади». 14 жовтня 2026 року спрацювали алерти.
   У теці — усе, що є про цей інцидент. Що сталося і чому? Назви першопричину,
   наскільки ти впевнений і на які дані спираєшся.
   Відповідь дай повністю в чаті; файлів не створюй і уточнювальних питань не став —
   припущення називай явно.
   ```

3. `docs/rca.md` (шаблон є): хронологія; першопричина; таблиця доказів
   «твердження → команда → результат» — кожен рядок можна повторити з кореня репо;
   **що з даних НЕ є причиною — і чим це доведено**: кожна причина, яку назвав хоч один
   прогін AI і яку ви відкинули, і те, що підозрювали ви самі; чинники, що сприяли;
   впевненість. Наприкінці — порівняння `rca-v1` і `rca-v2`.
4. `docs/postmortem.md` (шаблон є): blameless — про систему і процес, а не про людей;
   action items з типом **prevent / detect / mitigate**, власником-роллю і способом
   перевірити, що зроблено.
5. `docs/runbook.md` (шаблон є): runbook для цього класу алертів — для чергового, який
   цього інциденту не бачив.

Корисні команди (Git Bash, з кореня репо) — форма, а не відповідь; підставляйте свої файли й поля:

```bash
# які повідомлення є в лозі і скільки разів
grep -o '"msg":"[^"]*"' incident/logs/api-2026-10-14.jsonl | sort | uniq -c | sort -rn

# події рівня error по годинах (символи 19–20 рядка — година в "ts")
grep '"level":"error"' incident/logs/api-2026-10-14.jsonl | cut -c19-20 | sort | uniq -c

# те саме по хвилинах — для хронології (символи 19–23 — ГГ:ХХ)
grep '"level":"error"' incident/logs/api-2026-10-14.jsonl | cut -c19-23 | uniq -c | head -20

# середнє і максимум колонки метрик у проміжку часу: файл, колонка, від, до
node -e '
const [file, col, from, to] = process.argv.slice(1);
const [head, ...rows] = require("fs").readFileSync(file, "utf8").trim().split("\n");
const i = head.split(",").indexOf(col);
const v = rows.map((r) => r.split(",")).filter((r) => r[0].slice(11, 16) >= from && r[0].slice(11, 16) < to).map((r) => +r[i]);
console.log(col, from + "-" + to, "avg", (v.reduce((a, b) => a + b, 0) / v.length).toFixed(1), "max", Math.max(...v));
' incident/metrics/2026-10-14.csv p95_ms 12:00 13:00
```

**Число:** що назвав першопричиною прогін 1 і що — прогін 2, з якою впевненістю; чи
збігається кожен з вашим RCA; що в додаткових даних вплинуло на відповідь (або чому не вплинуло).

**Перевірка:** обидва файли в `ai-runs/`; кожне твердження в `docs/rca.md` має команду і
результат; є розділ «що НЕ є причиною» з доказом для кожного пункту; post-mortem без
пошуку винних, кожен action item має тип, власника і спосіб перевірки; runbook з
конкретними командами.

## Task D — Деплой і CI з AI + детерміновані перевірки _(~45 хв)_

**Мета:** AI пише конфіг деплою швидко, а перевіряє його детермінований перевіряльник,
а не враження. Плюс одна власна перевірка — з уроку вашого post-mortem.

1. **Перша чернетка AI.** Прогін бачить лише `app/`, `deploy/` і порожню теку `pipeline/` —
   без `tools/`: ми міряємо, що AI робить сам, а не як підганяє відповідь під перевірки.
   ```bash
   mkdir -p ../ws11-d/pipeline && cp -r app deploy ../ws11-d/
   ```

   ```text
   Підготуй деплой цього сервісу до продакшну: посиль deploy/Dockerfile і deploy/compose.yaml
   і напиши pipeline/deploy.yml — workflow GitHub Actions: тести → збірка образу → деплой
   із ручним погодженням через environment:, мінімальні permissions, секрети лише через
   ${{ secrets.NAME }}.
   ```

   Поверніть файли в репо і збережіть вивід перевірки **першої** чернетки. Якщо AI поклав
   workflow у `.github/workflows/`, у другому рядку візьміть його звідти:
   `cp ../ws11-d/.github/workflows/<файл>.yml pipeline/deploy.yml`.
   ```bash
   cp ../ws11-d/deploy/Dockerfile ../ws11-d/deploy/compose.yaml deploy/
   cp ../ws11-d/pipeline/deploy.yml pipeline/
   node tools/check-deploy.mjs > ai-runs/check-deploy-v1.txt; cat ai-runs/check-deploy-v1.txt
   ```

2. **Ітеруйте до всіх PASS** — уже в репо: давайте AI вивід `npm run check:deploy` і
   просіть виправити. Чесні правила гри: не змінюйте наявні правила в `tools/`, не
   видаляйте сервіси і не вимикайте перевірки, щоб «пройти». Секрети в compose —
   посиланням `${VAR:?…}` з оточення: застосунок і так читає їх зі змінних оточення, тож
   `app/` чіпати не треба. Кожну зміну, яку лишаєте, ви маєте вміти пояснити.

3. **Ваше правило.** Візьміть **один** action item зі свого post-mortem, який можна
   перевірити детерміновано по файлах репо, і зробіть з нього **нове** правило в
   `tools/check-deploy.mjs` (як додати — у шапці файлу; ID — свій, не з наявних) з
   тестом у `tools/test/check-deploy.test.mjs` або в новому файлі
   `tools/test/<назва>.test.mjs` — файл з іншою назвою `npm run test:tools` не запустить.
   У тесті — щонайменше два випадки:
   - фікстура, що відтворює ситуацію з інциденту, — **FAIL**;
   - коректна конфігурація, до якої наївна версія правила причепилася б, — **PASS**.
     Правило має ловити саму проблему, а не все, що на неї схоже: так наявне правило D3,
     коли `HEALTHCHECK` є в образі, дозволяє сервісу без `ports:` його вимкнути, а сервісу
     з `ports:` — ні.

   `npm run test:tools` — зелений; `npm run check:deploy` — усе PASS, з вашим правилом.
   Що ловить правило і чому воно спіймало б цей клас проблем, а не лише цей інцидент, —
   у розділі «Action item → правило перевірки» вашого `docs/postmortem.md`.

> `pipeline/deploy.yml` лежить у `pipeline/`, а **не** в `.github/workflows/`: так він
> не запуститься ні в репо курсу, ні в чужих форках.

**Число:** скільки правил провалила перша чернетка AI (з `ai-runs/check-deploy-v1.txt`).

**Перевірка:** `npm run check:deploy` — усе PASS; `pipeline/deploy.yml` — у `pipeline/`;
